# LLM Wiki 健康评分固定探针问题集

本文件用于语义抽样阶段。评估者应在每次评分中尽量使用同一组探针问题，避免每轮随意提问导致分数不可比较。探针问题不是唯一问题；如果知识库主题特殊，可以补充问题，但不得跳过本文件中与维度相关的标准问题。

## 使用规则

- 每个维度至少回答 2 个探针问题；`knowledge_sedimentation_effectiveness` 和 `retrieval_answerability` 至少回答 4 个。
- 每个回答必须记录 evidence：`file` 指向被检查文件，`note` 说明为何支持或削弱评分。
- 评分时优先读取样本文件，再沿样本中的 source、raw、core note、规则文件或索引链接追溯证据。
- 如果探针问题无法在知识库中找到证据，应记录为风险，不要用常识补齐。
- 横向比较时保留同一套问题；纵向比较时尽量复用上一轮样本范围。

## 架构符合度

1. 根目录是否能清楚识别 raw、wiki、schema、日志或维护入口？
2. AGENTS/RULES 等 schema 是否说明资料从 raw 到 wiki 的沉淀路径？
3. 知识库是否定义 ingest、query、lint、refresh、validate、reconcile 或等价维护流程？
4. 关系维护协议是否能让 agent 判断哪些链接是人工知识、哪些是自动生成关系？

## 来源可追溯性

1. 抽样 wiki 结论是否能回到 raw source 或 `.core.md` 旁注？
2. 结论与 source 内容是否一致，是否存在未被 source 支撑的扩展判断？
3. 引用粒度是否足够细，能否定位到具体文件、会议、附件或段落？
4. source 文件缺失、重命名或移动时，是否仍有可恢复路径或旁注证据？

## Schema 治理质量

1. schema 是否完整说明角色、分层、取信顺序、写入边界和维护流程？
2. 不同规则文件之间是否存在冲突、重复或无法执行的模糊表述？
3. agent 是否能根据 schema 做出一致判断，而不依赖主观猜测？
4. schema 是否包含可验证条件，例如 marker、字段、命名、日志和校验命令？

## 知识沉淀有效性

1. 最新 wiki 页面是否把原始资料压缩成长期可复用知识，而不是简单搬运？
2. 页面是否保留关键背景、适用边界、结论依据和后续行动？
3. 多个 source 之间有冲突时，页面是否说明冲突和取信顺序？
4. 页面是否足够连贯，未来 agent 或人类能直接用于回答问题或推进工作？
5. 页面是否把临时过程信息与稳定结论区分开？
6. 新沉淀内容是否能链接回已有知识，形成复利而不是孤立笔记？

## 检索与回答可用性

1. 用户提出主题型问题时，是否能从入口、索引或链接快速找到候选上下文？
2. 对事实型问题，知识库是否能提供忠实、可引用的答案？
3. 对决策型问题，知识库是否能提供边界、依据、风险和下一步建议？
4. 同名文件、悬空链接或路径歧义是否会阻碍 agent 找到正确材料？
5. 最新沉淀页面是否能回答“这件事现在是什么状态、为什么、下一步是什么”？
6. 索引、标签或链接是否能支持跨主题组合查询？

## 维护与演化健康度

1. log 或等价日志是否记录最近维护日期和维护动作？
2. 过期、悬空、歧义、冲突或低价值内容是否有检测和修复流程？
3. 自动生成块、旁注和机器索引是否有 marker，能否安全刷新？
4. schema 变化后，是否有重建、校验和回滚或恢复路径？

## 记录建议

语义抽样时，可在 `semantic_scores.json` 的每个维度中记录如下信息：

```json
{
  "probe_question": "抽样 wiki 结论是否能回到 raw source 或 .core.md 旁注？",
  "answer": "能 / 部分能 / 不能",
  "file": "wiki/example.md",
  "note": "该页面正文链接到 raw/source.pdf.core.md，但缺少具体段落级说明。"
}
```
